**Ялгаа — интерфейсийн алдаа vs oracle-ийн алдаа:** DOWN тохиолдолд серверт
огт хүрч чадаагүй тул энэ бол сүлжээ/холболтын (interface) алдаа — манай
API-гийн логикт (oracle) ямар ч хамаагүй. Харин FAIL тохиолдолд сервер хариу
өгсөн ч бидний хүлээж байсан утга (oracle) буруу байсан — энэ бол логикийн
алдаа. Хоёр нь өөр шалтгаантай ч аль алинд нь CI pipeline зогсох ёстой
(exit code ≠ 0).

## 5. Дүгнэлт

Энэ лабораторид тест дизайны 5 алхмыг (функц тодорхойлох → сонголт →
утга → спецификаци → бодит тест) бодит REST API дээр хэрэгжүүлэхэд
хамгийн их бодол шаардсан хэсэг нь сонголт (equivalence class)-уудыг
зөв тодорхойлох байлаа — ялангуяа studentID, coursesTaken, courseID,
prerequisites дөрвөн хувьсагчийн хослолыг системтэйгээр барагдуулах нь
гадны харцаар бодож байснаас илүү өргөн асуудал байсан. Хамгийн
сонирхолтой тохиолдол бол Спецификаци 9 (давхар алдааны хослол) байлаа:
идэвхгүй оюутан, байхгүй хичээл хоёр алдаа зэрэг тохиолдоход систем аль
алдааг түрүүлж буцаахыг зааварт тусгайлан заагаагүй тул өөрөө тест бичиж
л олж мэдэх ёстой байлаа — серверийн кодыг унших эсвэл туршилтаар
шалгахгүйгээр урьдчилан таамаглах боломжгүй зүйл байсан нь тестийн
чухал ач холбогдлыг харуулж байна. Хязгаарын тохиолдол (prerequisites
хоосон үед) мөн анхаарал татсан — энгийн логикоор бол алдаа гарах мэт
санагдах ч, хоосон массив дээрх .filter() үргэлж хоосон буцаадаг тул
амжилттай бүртгэл болдог нь кодын нарийн зан төлөвийг олж харуулсан.
Техникийн талаас Bruno-гийн "хадгалагдаагүй tab" (unsaved •) асуудал
анхны bru run-ыг бүрэн эвдэж, Body/Tests хоосон экспортлогдсон нь
GUI-based хэрэгслийн нуугдмал эмзэг тал болохыг олж мэдсэн — үүнийг
бүх tab-аа Ctrl+S-ээр хадгалж засав. PASS/FAIL/DOWN гурван
ажиллуулалт хоорондын ялгаа (0/1/1 exit code боловч FAIL нь логикийн
алдаа, DOWN нь холболтын алдаа) CI/CD-ийн quality gate-ийн ач
холбогдлыг тодорхой харуулсан. Ерөнхийдөө энэхүү лаб нь тест дизайны
онолыг (сонголт, утга, спецификаци) бодит, ажиллаж байгаа кодтой
холбож, "яагаад яг энэ тестийг бичих ёстой вэ" гэдгийг ойлгоход
тусалсан.
